## 1. 試験対象の境界

テストは、Server単体、Server–Agent契約、Agent単体、実ECU結合、MCP利用、走行中切替の段階に分離する。**合成入力の成功を実ECU取得成功として扱わない**。ChatGPT通常／Liveのツール利用実績も、クライアント側の継続実行・自発発話の保証とは区別する。

要件IDごとのテストへの紐付けは[要件トレーサビリティ表](requirements_traceability.md)に保存し、各バージョンの実装・テスト時に結果（未実行／合格／失敗／対象外／条件付き）を追記する。原本を誤ACKする重大不具合、安全外のコマンド実行、認可漏洩はリリース阻止条件とする。

本表のP0/P1/P2はテストの優先度であり、SRSの必須／目標／任意を上書きしない。

## 3. Server受信基盤の契約テスト（Phase 1）

| ID | 前提・刺激 | 期待結果 |
| --- | --- | --- |
| CT-001 | 有効端末＋登録済profile＋1バッチ | DB commit後のみ200 committed、件数一致 |
| CT-002 | 同じrecord ID／同じ本文を何度も再送 | 既保存扱い、原本と検索射影は1件 |
| CT-003 | 同record IDだが値・run・source_kindが異なる | 409、既存原本変更なし、バッチ全体未ACK |
| CT-004 | 同run＋sequenceを別record IDで送る | 409、既存原本維持 |
| CT-005 | 観測／イベント／gapの各kindでIDを再利用 | 409、共通record registryで拒否 |
| CT-006 | バッチ100件の途中1件だけ不正 | 422、100件ともcommitなし |
| CT-007 | 422後に問題recordを隔離し99件を再送 | 正常99件ACK、隔離1件はローカル保持 |
| CT-008 | commit直前DB障害 | 成功ACK無し、DB復旧後再送で原本保全 |
| CT-009 | commit後、応答をネットワーク遮断 | 再送はduplicate成功、二重レコードなし |
| CT-010 | 不正トークン、別vehicle、失効トークン | 401/403、データ閲覧／保存／操作不可 |
| CT-011 | profile_revision未登録・項目ID不一致 | 拒否。定義登録後に同IDで再送できる |
| CT-012 | 異常JSON、無限大、null、不正単位、413超過 | 未保存データはACKされず、問題特定可能 |
| CT-013 | 2 Agent、同車両へ並列再送 | 同じrecord IDが1件に収束 |
| CT-014 | 後から古い時刻のsampleを送る | 元の観測時刻・sequenceを保持して登録 |
| CT-015 | 大量滞留中に新しい観測を連続送信 | 最新と過去の送信処理がともに進行 |
| CT-016 | syntheticとecu source_kindを混ぜる | 実ECUとして誤認されず、検索で区別 |
| CT-017 | runが再起動で変化 | sequenceの重複が異run間では合法 |
| CT-018 | 状態報告を新しい順→古い順で送信 | stale表示が退行しない |

このPhaseの**受入条件**は、合成テストからServerのDB原本・検索・ACKの整合を確かめられること。実ECUやMCP接続は不要。

## 4. Agent・オフライン保全（Phase 2）

| ID | 操作 | 期待 |
| --- | --- | --- |
| AG-T01 | RRBridgeの既存selftest | フック／受け皿の取扱いに回帰がない |
| AG-T02 | writer永続化後Agentを強制終了 | record ID／payload／未ACKが復旧 |
| AG-T03 | 保存済み未ACKでServer停止・回復 | 全件再送、重複無し |
| AG-T04 | SQLiteのACK状態更新直後電源断模擬 | 未ACK誤削除なし、重複再送は安全 |
| AG-T05 | 最新優先中、古いpendingを大量作成 | 新旧の送信処理に飢餓なし |
| AG-T06 | キュー満杯、disk full、SQLite破損 | 失敗とloss/gapを可視化し、保存成功と偽らない |
| AG-T07 | スプール定義送信失敗 | 観測を保持し、profile登録成功後に再送 |
| AG-T08 | 同command再配送／Agent再起動 | ローカル台帳・実機照合なしに二重実行しない |
| AG-T09 | 手動操作介入・AI停止CLI | AI自動変更を止め、基本ロギングとspool保護を維持 |

| AG-T11 | 外部Server、認証無し・失効 | データ漏洩せずローカル保全継続 |

Agentは**実ECU取得の前**に合成データで上記を確認する。WindowsとRomRaiderの実バージョン差異は別試験。

## 7. 非機能・性能測定

| 観測量 | 採取する値 | 初期評価の考え方 |
| --- | --- | --- |
| ECU更新周期 | Hz、中央値、P95、最大取得間隔、取得項目／通信定義 | ECUと選択項目で異なる。普遍Hz保証なし |
| 車載writer遅延 | 取得通知→spool commit、queue depth、drop | DB／HTTPを取得コールバックで待たない |
| 転送遅延 | spool commit→Server commit、P50/P95 | **P95 2秒**は暫定設計目標、過去滞留と切り離す |
| 再送回収率 | 経過時間ごとのbacklog減少、最新データの鮮度 | 回収と最新の両方が進行する |
| API/DB | リクエスト処理時間、commit時間、ロック待ち、SQL実行計画 | 機器規模に応じ調整 |
| MCP検索 | 上限内のSQL実行、ページ容量、cursor継続、タイムアウト | 原本に全量到達でき、資源枯渇なし |
| disk逼迫 | 未ACK bytes、空き容量、warning/error | OS領域保護・未ACK自動削除無し |
| worker | 監視処理遅延、イベント重複率 | LLM無し継続、exactly once相当の冪等イベント |

## 8. テストデータ管理と結果様式

- 合成fixtureでは、元データの期待値とID・sequence・profile版・source_kindを明示する。
- 実ECU試験は試験日、対象車両、RomRaider・OpenPort・Logger定義、Agent/Serverコミット、条件、サンプル数、失敗・取得Hz・Server保存数を記録。
- 車両個体やパスワード、トークン、会社用メールアドレス、不要な生ログを公開リポジトリへコミットしない。個人特定情報は適切に秘匿してから実験記録を公開。
- 各テストには試験ID、関係SRS ID、バージョン、実施方法、期待／実結果、pass/fail/not-run、証跡IDを付与。
- 自動テストは小規模でよく、P0の受信保全／認可／安全の基本ケースは毎CIで実行できるようにする。
- テスト未実施を「合格」と表記しない。実ECU・実走行・Live検証はそれぞれ区分を記録。

## 10. リリースを止める条件

原本未保存なのにACKを返す、未ACKを自動削除する、合成と実ECUを混同する、他車両のデータが漏洩する、無許可ECU操作が成立する、期限切れコマンドが無条件に実行される、実車で未検証の走行中切替を自動有効化する――これらはいずれも設計目的に反する重大な不具合として扱い、原因解消・回帰試験まで公開運用を停止する。
