> この文書は、2026-10-12までのユーザーとの要件検討で合意した**製品全体の要求**をまとめる。既存PoCの制約・実装上の便宜・過去の検討メモと食い違う場合、**今後実装する製品の要求としては本書を優先**する。ただし、実装や実機の安全機構を本書だけで解除してはならない。接続規約の現行実装上の正本は [RomRaider_agent/docs/10_interfaces.md](https://github.com/zawa356/RomRaider_agent/blob/main/docs/10_interfaces.md) とし、変更時には実装と同時に更新する。

## 1. 目的・背景

### 1.1 解決したい課題

RomRaider Loggerの計測項目・プロファイルの手動変更は煩雑であり、とくに運転中はPCを操作できない。K-Line/SSMでは取得項目数・応答量によって更新周期が悪化し、過大な設定ではデータ収集そのものが成立しなくなる可能性がある。ログを後からファイル単位で読むだけでなく、走行中から継続的に保存し、ChatGPTの会話から計測・解析を支援してほしい。

### 1.2 達成したい姿

運転者が「燃調を見たい」「加速時の過給圧を調べたい」など**自然言語で調査目的を伝える**と、AIが利用可能なECUパラメーターを調べ、計測計画とプロファイルを提案・生成し、許可された範囲内で計測項目の変更・結果解析・再計測を支援する。ユーザーはパラメーターIDやバイト数を通常意識しない。走行中のPC操作を要求せず、会話をしていない間も基本計測・蓄積・数値監視は継続する。

**対象はECUテレメトリーの読み取り・収集・評価であって、ROMチューニングや車両制御ではない。**

### 1.3 開発・提供の前提

- 個人利用を第一とする**セルフホスト型ソフトウェア**。開発成果をGitHubで共有・公開可能にする。ホスト型の他人向けサービス運営、多人数テナント管理は目的としない。
- 車載側はWindows上のRomRaider Logger利用を前提とする。サーバーはLinux上のDockerによる自己運用を想定する。特定VPS事業者・ホスト・PC・車種に固定しない。
- 最初の検証組合せは **レガシィBP5／ThinkPad X270／OpenPort 2.0互換機／RomRaider・RRBridge／ChatGPT通常チャット・Live** とする。他車種・他Windows端末での全面的な動作保証は求めない。
- 高額なAPI従量課金に依存しない。AI推論は利用者のChatGPTサブスクリプションのチャット・Live利用を主とし、サーバーは独立した常時LLM実行を行わない。
- 文書は**要件（何を／なぜ／どこまで）**を規定する。具体的なクラス、APIパス、DBテーブル、ライブラリ、秒数閾値、認証プロトコルの決定は基本設計以降とする。

## 2. 用語・責任分界

| 用語・構成要素 | 意味／主な責任 |
| --- | --- |
| RomRaider Logger | ECUへの読み取り診断通信と計測の既存アプリケーション。製品版も本体改変を前提としない。 |
| 車載クライアント | RomRaider連携と計測監視・ローカル保全・サーバー連携を担当するWindows上の構成要素（RRBridgeや制御監督処理を含む概念）。 |
| RomLogger Server | 車載データの受信・永続保存、検索・統計処理、品質監視、異常イベント、計測要求の配送・状態管理、MCP提供を担当するセルフホスト側。 |
| AIクライアント | ChatGPTを中心とするMCP対応の対話エージェント。高度な解釈・計測計画立案を行う。 |
| 走行セッション | 一連のエンジン始動から停止までの走行・計測の論理単位。原則自動生成。 |
| 計測タスク | 「燃調調査」等の目的・承認範囲・経過・成果。走行セッションをまたいで継続可能。 |
| 計測区間（セグメント） | 同一の計測定義が適用された時間的区間。プロファイル変更で区切り、切替中の欠測も識別する。 |
| 計測プロファイル | 実際にRomRaiderへ適用する、計測対象パラメーターの構成。 |
| 生データ | 取得時のサンプルと元の時間情報・パラメーター情報。統計・間引きで置換されていない記録。 |
| 承認範囲 | 利用者が事前に承認した計測目的・変更可能範囲・期間等。車載安全条件とは独立した認可条件。 |
| フォールバック | 品質悪化等で、適用前に正常性を確認したプロファイル等へ安全に復帰すること。 |

責任境界の原則：**ECU通信・安全判定・データ保持は車載側でも独立して成立**させる。サーバーは全体の蓄積と監視、AIは高度な判断を担当する。MCPツールの存在はAIの自律起動・ツール呼び出し・発話の保証ではない。

## 3. 優先度・適用範囲

- **必須**: 初版の中心要件。未実装なら機能として達成済みと表記しない。
- **目標**: 望む機能・品質だが外部のAIクライアント仕様や実機検証等の制約を受ける。達成条件を設計・検証時に確かめる。
- **任意／将来**: 初版の成立に必須ではない拡張。

以下の表で特記のないものは**必須**とする。

## 4. 機能要件

### 4.1 動作モードと基本ロギング（FR-OPS）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-OPS-001 | Windowsクライアントは**通常のRomRaider手動利用モード**と**AI／サーバー連携モード**を選んで起動できること。 | 必須 |
| FR-OPS-002 | モードの選択は起動時に行い、運用中の動的切替は要求しない（切替には再起動してよい）。 | 必須 |
| FR-OPS-003 | AI連携モードでは、計測開始・継続・プロファイル管理を連携機構が管理し、通常運用で利用者の同時手動変更を想定しない。競合・外部変更を検知したら安全側に扱うこと。 | 必須 |
| FR-OPS-004 | AI接続やアクティブな計測タスクがなくても、利用可能な状態では基本ロギングを継続すること。 | 必須 |
| FR-OPS-005 | 計測タスク終了後は基本計測に戻り、走行履歴を蓄積し続けられること。 | 必須 |
| FR-OPS-006 | 車載PCで常時GUI操作を必要としないこと。クライアント運用・設定はCLI等の軽量な操作を基本とし、独自GUIを必須にしない。 | 必須 |
| FR-OPS-007 | AIによる自動変更を停止・抑止できる独立した操作手段を持つこと。停止中でも可能な限り既存ログを保全すること。 | 必須 |

### 4.2 利用可能な項目の自動発見・初期設定（FR-CAP）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-CAP-001 | 車載側でRomRaider／Logger定義から利用候補のパラメーター情報を**自動取得**できること。 | 必須 |
| FR-CAP-002 | パラメーターID、名称、単位、定義・選択可能性等をサーバーへ自動同期し、AIから参照できること。 | 必須 |
| FR-CAP-003 | 定義・接続先・対応可否の変更を検出して更新できること。 | 必須 |
| FR-CAP-004 | 定義ファイルに存在するだけの項目と、現接続ECUで実際に取得できることが確認された項目を区別できること。 | 必須 |
| FR-CAP-005 | AIが未定義・未対応のパラメーターを想像でプロファイルに混入させても適用されないこと。 | 必須 |
| FR-CAP-006 | 車両・ECUの情報は可能な限り自動識別し、手動設定は自動判別できない項目やサーバー接続・認証等の最小限にすること。 | 必須 |
| FR-CAP-007 | 初期のBP5専用値・PC固有パス等を一般製品の必須設定として固定しないこと。 | 必須 |

### 4.3 AIによる計測タスク・プロファイル管理（FR-PLAN）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-PLAN-001 | 利用者は自然言語で計測目的を指示でき、AIが具体的なパラメーター選択や計測計画へ落とし込めること。 | 必須 |
| FR-PLAN-002 | AIは利用可能なパラメーター定義・過去ログ・品質情報を参照し、適合する計測プロファイルを生成・提案できること。 | 必須 |
| FR-PLAN-003 | 利用者はタスク開始時に目的と許容範囲を**包括承認**でき、同範囲の個別変更ごとに運転者の再承認を要求しないこと。範囲外は承認を求めること。 | 必須 |
| FR-PLAN-004 | 包括承認はECU安全条件の免除ではない。AIの指示・承認済み範囲・車載側検証の**全条件**を満たして初めて操作可能とすること。 | 必須 |
| FR-PLAN-005 | AIは計測目的と通信帯域・応答速度の実測に応じ、基本項目も含めて取得項目を増減・入替できること。基本パラメーターを固定・必須とはしないこと。 | 必須 |
| FR-PLAN-006 | 変化が速い信号の時間分解能を原則重視しつつ、相関解析に必要な同時計測と帯域制約のバランスをAIが判断できること。 | 必須 |
| FR-PLAN-007 | プロファイル適用後は更新周波数・間隔・欠損・ECU通信・転送品質を確認し、必要なら計測計画を再評価できること。 | 必須 |
| FR-PLAN-008 | AIがユーザーへ案内する内容は、計測目的、主要な結果、次の計測条件等の意味ある節目を中心とし、保存・再送等の内部処理を逐一発話しないこと。 | 必須 |
| FR-PLAN-009 | AIは不足するデータに対し、市街地・巡航・緩やかな加速等の**適切な観測条件**を提案できるが、交通法規違反・危険運転を指示せず、運転判断は利用者に委ねること。 | 必須 |
| FR-PLAN-010 | 数分程度（例: 約5分）の計測後に十分性を評価して次の取得へ進む対話上の流れを目標とする。ただし**時刻だけで十分と判断せず、観測条件とデータ品質を考慮**すること。 | 目標 |
| FR-PLAN-011 | ChatGPT Liveからの自発的な定期呼び出し・割り込み音声発話は保証できないため、未検証の自動起動を初版の必須動作としないこと。 | 必須（制約） |
| FR-PLAN-012 | AIからの計画は検証可能な操作要求として受け付け、受理・保留・適用・拒否・失敗・期限切れの結果を追跡できること。 | 必須 |

### 4.4 安全・車載側の変更制限（FR-SAFE）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-SAFE-001 | **ECU／ROMへの書込み・フラッシュ、ROM読書き、ECUリセット、DTC消去・学習値リセット、アクティブテスト、OpenPort FW変更などを製品機能として提供しない**こと。許可操作は計測参照・ロガー記録制御・安全なプロファイル切替に限定すること。 | 必須 |
| FR-SAFE-002 | 走行中も計測プロファイルの自動変更を行えることを製品の**目標動作**とする。停止時限定を最終仕様として固定しないこと。 | 必須（目標動作の定義） |
| FR-SAFE-003 | 実装上の走行中許可は、実ECU通信・ロガー動作を確認した独立の車載安全条件を満たす操作に限る。確認前にPoCの停車ガードを無条件で解除しないこと。 | 必須 |
| FR-SAFE-004 | **切替に伴う計測ダウンタイム・欠測は許容**する。連続無停止計測は要求しない。一方、**切替前に取得済みのデータを消失させない**こと。欠測時間は欠測と明示すること。 | 必須 |
| FR-SAFE-005 | 生成プロファイルは適用前に定義整合性、項目数・通信負荷、操作許可範囲、状態・安全条件を検証すること。 | 必須 |
| FR-SAFE-006 | AIが選ばなかった項目を使う安全判定は成立したと推定しないこと。必要情報が欠ける場合は当該操作を拒否・保留するか、独立した信頼可能な情報源で判定すること。 | 必須 |
| FR-SAFE-007 | 旧プロファイルで正常に取得できていたのに、切替後に更新周期・通信品質が有意に悪化した場合、安全に可能なら**直前の正常プロファイルへ自動復帰**すること。 | 必須 |
| FR-SAFE-008 | フォールバックが安全に実行できない場合、無制限に再試行せず自動変更を停止し、失敗状態を記録・通知可能にすること。 | 必須 |
| FR-SAFE-009 | サーバー側でデータ到着停止等を検知した場合、原因確認後にクライアントへ復旧要求を出せること。ただし最終的な適用・拒否は車載側が判断すること。 | 必須 |
| FR-SAFE-010 | サーバー側の未着と、ECU側の収集停止やインターネット断を区別し、未着のみを根拠にむやみにプロファイルを変えないこと。 | 必須 |
| FR-SAFE-011 | 過去の操作要求を重複・期限切れ・承認範囲外のまま実行しないこと。実行完了の確認前に成功と報告しないこと。 | 必須 |
| FR-SAFE-012 | 走行中に画面確認・PC操作を要求せず、運転者への情報提示は簡潔にして注意散漫を避けること。 | 必須 |
| FR-SAFE-013 | 取得したログや統計から故障を安易に断定しない。計測未成立・疑似データ・欠損・推測の区別を維持すること。 | 必須 |

**注記（過去仕様との差）**: PoCの`docs/requirements.md` やSupervisor試験仕様には停車確認・短時間の手動アームを要求する記述がある。これは当時の実車安全ガードであり、**ユーザーが新たに合意した「走行中でも条件付きで変更する」という製品要件を満たしたことにはならない**。走行中の許可条件・検証方法は未確定として設計・実機評価する。

### 4.5 データ取得・長期保存（FR-DATA）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-DATA-001 | RomRaider稼働中、CSVの記録状態に依存せず取得可能なテレメトリーを継続収集・サーバー転送できること。 | 必須 |
| FR-DATA-002 | **取得済みの全サンプルを間引き・集約で置き換えず、ロスレスな原本としてサーバーDBへ保存**すること。 | 必須 |
| FR-DATA-003 | 元の時刻・サンプル順序・計測パラメーターID・名称・単位・適用プロファイル・区間を追跡可能にすること。 | 必須 |
| FR-DATA-004 | サーバーを長期保存の**正本**とする。通常運用で保存済み原本を自動期限切れ削除しないこと。 | 必須 |
| FR-DATA-005 | 車載側のローカルバッファ／spoolは転送完了まで保護し、保存完了の確認を受けて送信済みとして扱うこと。無期限の二重保管は必須にしない。 | 必須 |
| FR-DATA-006 | 再送時の冪等性・重複排除・欠番／欠落検知・送信失敗の可視化を提供すること。 | 必須 |
| FR-DATA-007 | 計測区間・プロファイルの変更にまたがって時系列を再構成でき、計測していない期間を実測値として補完したと誤認させないこと。 | 必須 |
| FR-DATA-008 | デバイス・車両を識別でき、複数台のログが混同されないこと。 | 必須 |
| FR-DATA-009 | データの集約・統計・可視化用加工は原本を変更せず別扱いとすること。 | 必須 |
| FR-DATA-010 | 転送・保存の限界でデータ喪失が生じた場合、無かったことにせず欠損・ドロップ件数・原因を確認可能にすること。 | 必須 |

「ロスレス」は**アプリケーションが取得できたサンプルを不用意に捨てない**という要求であり、ECUが未応答の期間や切替中に未取得だった値を作り出すこと、電源断・ディスク物理破損でも絶対無損失を保証することを意味しない。外部DBの物理バックアップ・レプリケーション・ストレージ設計は本アプリの別プロジェクトの責務。

### 4.6 オフライン・障害復旧（FR-RES）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-RES-001 | サーバー停止・回線断・MCP未接続でも車載側は可能な限り計測を継続すること。 | 必須 |
| FR-RES-002 | 接続断中は直前の正常計測構成を基本的に維持し、**AIからの新規計画変更は一時停止**すること。 | 必須 |
| FR-RES-003 | 車載側はサーバーがなくても計測品質を監視し、独立の安全条件に従って局所的なフォールバックができること。 | 必須 |
| FR-RES-004 | 未送信データを安全に蓄積し、回線復旧後に自動再送してサーバー保存へ追いつけること。 | 必須 |
| FR-RES-005 | 再送・再接続・再起動後の重複処理、未完了要求、古い命令の誤実行を防止すること。 | 必須 |
| FR-RES-006 | 再接続後はサーバーと実際のロギング状態を照合し、AIによる計画の続きを再開可能にすること。 | 必須 |
| FR-RES-007 | 自動復旧・再試行は上限と失敗の可観測性を持ち、永久ループや誤った「復旧成功」を避けること。 | 必須 |
| FR-RES-008 | サーバーからの操作要求は車載側からのアウトバウンド通信等で受け取れること。車載PCへの公開着信ポートを必須としないこと。 | 必須 |

### 4.7 走行・タスク・履歴管理（FR-SESSION）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-SESSION-001 | 走行セッションは原則として自動で開始・終了・識別できること。 | 必須 |
| FR-SESSION-002 | 計測タスクは走行セッションと独立した概念とし、1回の走行に複数タスク、1タスクに複数走行を関連付けられること。 | 必須 |
| FR-SESSION-003 | 計測区間ごとのプロファイル・適用時刻・終了理由・変更契機・結果を追跡できること。 | 必須 |
| FR-SESSION-004 | 短時間停止・エンジンOFF判定等、セッション境界の自動判定に不確実性がある場合も履歴の整合性を維持すること。 | 必須 |

### 4.8 MCP・AI対話連携（FR-MCP）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-MCP-001 | AI向け共通インターフェースは**標準MCP**とし、固有のAIサービスやプロンプト実装に依存しないこと。 | 必須 |
| FR-MCP-002 | ChatGPTの通常チャット・Liveを初期の正式検証対象とし、他のMCPクライアントは基本互換を目指す。Claude等の個別音声モード保証は求めない。 | 必須／目標 |
| FR-MCP-003 | MCPから最新状態、セッション、パラメーター一覧、計測品質、期間データ、イベント、過去解析結果を参照できること。 | 必須 |
| FR-MCP-004 | MCP経由で計測計画の提出・要求・結果照会、AI解析結果の登録、監視条件の登録ができること。車載操作の実行判定はMCP／AIの外で行うこと。 | 必須 |
| FR-MCP-005 | **MCPを介したサーバーからChatGPTへの自発的なツール実行要求・推論開始・音声発話は保証しない**。AIへのプッシュを必須機能として記述しないこと。 | 必須（制約） |
| FR-MCP-006 | 通常チャット・Liveの範囲で利用し、バックグラウンドLLM API定期呼出しや従量課金を必要条件としないこと。 | 必須 |
| FR-MCP-007 | MCPツール呼出しの成功・失敗・操作の実行結果を区別し、操作がサーバーに登録された時点を車載側の完了と混同しないこと。 | 必須 |
| FR-MCP-008 | AIが会話開始時に未読の重要イベントを**要求して取得**できること。チャットを開いただけで必ず自動検索されるとは保証しない。 | 必須 |
| FR-MCP-009 | 一連の対話中にAIが数分おきの再解析・次計測を自発的に行う運用は目標とするが、MCPクライアント側の再呼出し・発話制約を検証すること。 | 目標 |

### 4.9 分析用データ提供（FR-ANL）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-ANL-001 | AIは期間・車両・走行セッション・パラメーターで絞った生の時系列データへアクセスできること。 | 必須 |
| FR-ANL-002 | サーバーは集計・統計・概要・時系列抽出等の補助機能を提供するが、**生データへの直接アクセスを妨げない**こと。 | 必須 |
| FR-ANL-003 | 長期間・大量の結果は分割・段階取得を可能とし、取得範囲・未取得範囲・切り詰めの有無を明示すること。 | 必須 |
| FR-ANL-004 | 時刻と項目間の相関・応答の順序・瞬間的な変化を解析できる時間情報を保持すること。 | 必須 |
| FR-ANL-005 | 品質指標・欠測・定義変更・同期ずれ・合成試験データの区別をAIが判別できること。 | 必須 |
| FR-ANL-006 | AIは必要なら概要を経由せず生データから直接解析を始められること。 | 必須 |
| FR-ANL-007 | AIの結論は単純集計結果よりも走行条件・比較条件・データの十分性を踏まえた解釈を重視すること。 | 必須 |

### 4.10 AI解析記録と知見の継続性（FR-HIST）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-HIST-001 | AIはMCP経由で解析結果・調査目的・計測計画・未解決事項をサーバーへ登録できること。 | 必須 |
| FR-HIST-002 | 記録には対象車両・セッション・期間・参照データ・根拠・結論・推測の程度を関連付けられること。 | 必須 |
| FR-HIST-003 | 異なるチャットから過去の解析結果・未解決事項を取得し、続きの調査に活用できること。 | 必須 |
| FR-HIST-004 | 解析結果は**追記型**で保持し、訂正・補足・撤回・再評価では元の記録を消さず関係を記録すること。 | 必須 |
| FR-HIST-005 | 過去の結論が現在有効か、訂正・撤回済みかを識別できること。 | 必須 |
| FR-HIST-006 | AIによる重要結果の自発的な登録は促進するが、クライアントが毎回保存ツールを実行する保証はないことを明示し、登録の成否を確認できること。 | 必須／目標 |

### 4.11 数値監視・異常検知・通知（FR-MON）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-MON-001 | ChatGPT非接続でもサーバーが継続的に数値的監視を行えること。 | 必須 |
| FR-MON-002 | サンプル到着停止、取得周波数低下、通信エラー、欠損・滞留等の計測品質異常を検知・記録できること。 | 必須 |
| FR-MON-003 | 車両値の外れ値、急変、持続的な逸脱、過去の計測との変化などを条件付きで検出できること。 | 必須 |
| FR-MON-004 | 既存の統計・時系列解析手法や実績あるライブラリを調査し優先利用すること。個別アルゴリズムは設計で選ぶ。 | 必須（方針） |
| FR-MON-005 | 走行状態依存性、センサ特性、単発ノイズ、欠測を考慮し、統計的な異常を故障診断と同一視しないこと。 | 必須 |
| FR-MON-006 | ChatGPTがMCP経由で監視条件を追加・変更でき、登録後はLLMを呼ばずサーバーで評価できること。 | 必須 |
| FR-MON-007 | イベントの時刻・重要度・対象条件・根拠データ・確認状態等を記録し、後からMCPで検索できること。 | 必須 |
| FR-MON-008 | Discord Webhook等への通知は**任意拡張**とし、採用時は重複抑制・頻度制限・通知不能時の記録を考慮すること。 | 任意 |
| FR-MON-009 | 通知は車載警報装置や車両安全監視システムの代替ではないことを明確にすること。 | 必須 |

### 4.12 セルフホスト・アクセス制御（FR-SEC）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-SEC-001 | 利用者自身がサーバーを展開・運用できること。複数人向けアカウント・テナント管理を必須としない。 | 必須 |
| FR-SEC-002 | 1サーバーで複数車両・複数車載クライアントを識別して管理できること。 | 必須 |
| FR-SEC-003 | 車載クライアント・MCP接続・管理者の資格情報と権限を区別できること。 | 必須 |
| FR-SEC-004 | ログ参照、解析記録の登録、監視条件の設定、計測操作要求、管理操作は適切に権限を分離すること。 | 必須 |
| FR-SEC-005 | 認証済みの安全な外部通信を前提とし、実車データや実操作を匿名の公開MCPから取得・実行できないこと。 | 必須 |
| FR-SEC-006 | DBをインターネットへ直接公開することを前提としない。任意SQL・OSコマンド・任意ファイル操作をMCP経由で無制限に公開しないこと。 | 必須 |
| FR-SEC-007 | 資格情報の発行・失効・差替えができ、秘密情報をGitHubコミット・ログやサンプル設定に含めないこと。 | 必須 |
| FR-SEC-008 | 認証の具体方式はMCPクライアント（特にChatGPT Live）の実対応を検証して選定する。ユーザー管理のためだけに複雑な認証基盤を自作することは要求しない。 | 必須（制約） |
| FR-SEC-009 | 誰が・どの計測操作を要求し・何が許可／拒否／完了されたかを追跡できること。 | 必須 |

| ID | 要件 | 優先度 |

| NFR-001 | 運転中の利用でPC操作を要求しないこと。会話・通知は運転への注意を妨げない内容とする。 | 必須 |
| NFR-002 | ECU計測レートとサーバー転送レイテンシーを混同せず、更新周波数、間隔の分位値、最新サンプル経過時間、ドロップ、送信失敗等を観測可能とする。 | 必須 |
| NFR-003 | 項目数・定義長・ECU応答等により品質が変わることを考慮し、固定Hz値や固定項目数を製品全体の普遍的な性能保証にしない。 | 必須 |
| NFR-004 | データ量に応じた段階取得・上限・ページング等でMCP応答の巨大化やサーバー資源枯渇を防ぎ、AIから必要な生データの全量へ到達可能とする。 | 必須 |

| NFR-007 | サーバーはLinux Dockerによる構築・更新・再配置を可能にし、特定のホスティング事業者への依存を避ける。 | 必須 |

| NFR-010 | ChatGPT/Claude等の従量課金LLM APIを利用しなくても、常時ログ収集・保存・監視が機能する。 | 必須 |
| NFR-011 | GitHubで第三者が導入できる程度のドキュメントを整備しつつ、他人向け運用保守や全環境へのサポート提供を約束しない。 | 必須 |
| NFR-012 | RomRaiderへの組込み・配布に関係するライセンス（GPL等）を公開前に確認し、無許可の第三者バイナリや資格情報を再配布しない。 | 必須 |

## 6. 対象外・初版で保証しないこと

- ECU ROMの読み取り・書き込み・チューニング・フラッシュ、DTCの消去、ECUのリセット、アクティブ制御、FW更新。
- 他人の環境をホストするSaaS、複雑なユーザー／テナント管理、専用の管理GUI、フル機能の車両診断装置。
- AIが会話していない間の**LLM推論の常時・定期実行**とそれに伴う従量課金API呼び出し。
- MCPを通じたChatGPTへの確実なプッシュ、Liveモードの自動発話開始、会話開始時の無条件の自動ツール呼出し。
- ECUから未取得の値の補完、プロファイル変更中の**ゼロダウンタイム**。
- 任意の車種・全ECU・全OpenPort互換機・全MCP音声クライアントでの動作保証。
- DBインフラの物理バックアップ、レプリケーション、ストレージ冗長化の設計（別の基盤プロジェクトの責任）。
- 商用システム相当の網羅的な受入試験書・完全な組合せ検証。

## 7. 最小限の検証方針

本ソフトウェアは個人利用を基本とし、**小規模な自動試験と実機の段階的な確認、利用中の不具合修正**を中心に品質を高める。全ケースの網羅的受入試験は要求しない。

ただし、次は主要なリスクに直結するため、適用前に最低限確認する。

| ID | 確認事項 |
| --- | --- |
| VAL-001 | 実ECUからのサンプル取得とサーバーDBへの保存を確認する（合成selftestの成功だけでは代用しない）。 |
| VAL-002 | プロファイル切替前に取得したサンプルが失われず、切替による欠測・区間境界が分かることを確認する。 |
| VAL-003 | 通信断中に車載側が記録を保持し、再接続後に再送でき、重複・欠番を確認できることを検証する。 |
| VAL-004 | AIやMCPが許可外のECU操作・任意コマンド・危険なプロファイルを実行できないことを確認する。 |
| VAL-005 | 走行中の切替は静止状態での実機検証から始め、ECU通信負荷・品質・復旧を評価した範囲でのみ段階的に解禁する。 |
| VAL-006 | 失敗時・通信断時・再起動後に古い指示を二重実行せず、クライアントの最終安全判定が働くことを確認する。 |

検証結果は**合成データ／実ECUデータ／実車走行**を区別して記録する。閾値・テストケース数・自動化方法の確定は設計・実装フェーズでよい。

## 8. 現PoCと製品要件の差分（2026-10-12時点）

**以下は要求実装の完了宣言ではない。** 既存リポジトリのREADME・設計・検証資料に基づく開発上の出発点。

| 領域 | 既存PoCで確認／実装されていること | 製品化の際に必要な差分 |
| --- | --- | --- |
| RomRaider外部制御 | RRBridgeで状態・ロギング・プロファイル切替が実機上で動作（当時ECU無応答の条件）。 | 目的別の自動生成・適合検証・車載安全監督・計画履歴。 |
| 転送・保全 | RRBridgeによるspool・HTTP転送、合成データでの再送を確認。 | 実ECUでの全経路・DB正本化・断線再開・ドロップ監視の整合性確認。 |
| ChatGPT Live／MCP | Android Live→一時デモMCPの呼出し、提案・管理者承認→X270プロファイル変更、合成データ20件の保存・読出しを実施。 | 実データ向け認証、包括承認、安全な無人適用、計測・解析の実運用。 |
| プロファイル安全性 | 固定候補・項目数ガード・停車／ロガー停止等のPoC制約。品質低下時復帰は単体試験中心。 | AI生成構成の検証、走行中の切替安全性、ローカル・サーバー双方の監視と復帰。 |
| 取得品質 | RRBridgeのstatus/healthにHz・間隔等の監視値がある。 | サーバー側での履歴化、異常検知・操作判断との連携。 |
| AI高度解析 | 最新値取得等のMCP PoC。 | 範囲指定生データ・統計・イベント・解析結果と訂正履歴。 |
| 利用条件 | 試験用の匿名Voice Demoは**合成データのみ**に限定。 | 実データ／実操作の匿名公開禁止。正式な認証方式は設計で決定。 |

旧PoC文書の「必ず停車」「常に管理者が1件ごとに承認」などを製品版の確定方針としてコピーしないこと。一方、現行PoCの安全チェックは新実装が検証されるまで残すこと。
